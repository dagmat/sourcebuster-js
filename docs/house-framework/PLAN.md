# План разработки: фреймворк внешней архитектуры дома

Основание: `TZ_v2.docx` (ТЗ, редакция 2 от 11.10.2026).
Статус: **черновик на утверждение**. Код не пишется, пока план не утверждён.

---

## 1. Как я понял задачу (коротко)

Веб-приложение, в котором заказчик без архитектурной подготовки:

1. проходит адаптивную анкету (блоки A–I, ответы тремя способами: значение, диапазон или «на усмотрение системы»);
2. получает проверенный бриф (JSON + JSON Schema, версии, источник и жёсткость у каждого параметра);
3. видит конфликты (проверки В-1…В-13) и варианты их разрешения, утверждает бриф;
4. получает не менее двух **автоматически сгенерированных** вариантов облика дома;
5. скачивает комплект из 10 позиций: PDF-альбом на листах A3 (ISO 5457/7200) и PNG-визуализации 3840×2160.

Главное архитектурное требование: **одна 3D-модель оболочки**. Из неё строятся и
визуализации, и чертежи (ФТ-11), и ведомости. Генерация детерминирована: один и тот же бриф
с тем же номером варианта даёт тот же результат (НТ-5).

## 2. Технологический стек

Принцип: **один язык (TypeScript) от анкеты до PDF**, минимум внешних сервисов,
всё поднимается одной командой `docker compose up`.

| Слой | Выбор | Зачем |
|---|---|---|
| Язык | TypeScript, Node.js 22 LTS | Один язык для фронта, бэка, геометрии и чертежей |
| Монорепозиторий | pnpm workspaces | Общие пакеты (схема брифа, геометрия) для фронта и сервера |
| Фронтенд | React + Vite, Mantine (UI), i18next (ru/en), TanStack Query | Анкета, удобная на телефоне (НТ-2), два языка (НТ-3) |
| 3D | Three.js | Интерактивный просмотр в браузере и рендер визуализаций на сервере **одним и тем же кодом** |
| API | Fastify + TypeBox | Схемы TypeBox одновременно дают TS-типы и JSON Schema брифа (ФТ-6) |
| Валидация JSON | Ajv | Проверка брифа и конфигураций по JSON Schema |
| БД | PostgreSQL 16 + Drizzle ORM | Бриф в JSONB, версии брифа и история изменений |
| Очередь задач | pg-boss (работает поверх Postgres) | Долгая генерация и выпуск идут в фоне, Redis не нужен |
| Конфигурация | YAML-файлы в репозитории, проверяемые по JSON Schema | Профили норм, стили, банк вопросов и правила добавляются без правки кода (ФТ-12, НТ-7) |
| Декларативные правила | json-logic-js + встроенные геометрические проверки | Простые правила задаются в конфиге; В-3, В-6 и другие геометрические проверки сделаны функциями, а их пороги берутся из профиля |
| Рендер PNG | Headless Chromium (Playwright) + Three.js, PBR-материалы, HDRI, тени | 4K-кадры без отдельного 3D-пакета. Blender (Cycles) можно добавить позже как опцию для фотореализма |
| Чертежи | Собственный модуль: SVG-листы из модели (ортогональные проекции, размеры, отметки, штриховки, основная надпись) | Полный контроль оформления по ISO 128/5455/5457/7200 |
| PDF | Chromium `page.pdf()` (точный A3 в мм) + pdf-lib (сборка альбома, титул, содержание) | Векторные чертежи без растеризации |
| ИИ-анализ изображений и документов | Claude API (vision) | ФТ-3: стилевые признаки из референсов. ФТ-5: параметры из ГПЗУ, топосъёмки и фото. Всё извлечённое показывается заказчику на подтверждение |
| Геокодирование | Nominatim (OpenStreetMap) | Адрес → координаты → регион и профиль |
| Авторизация | Email + пароль (argon2) или вход по ссылке из письма; сессии в cookie | Личный кабинет (ФТ-16) |
| Персональные данные | Шифрование полей и файлов на уровне приложения (AES-256-GCM), удаление по запросу | НТ-8 |
| Хранение файлов | Локальный том (на сервере) с шифрованием; позже можно перейти на S3-совместимое хранилище | Референсы, документы, готовые комплекты |
| Тесты | Vitest (модули), Playwright (сквозные сценарии), снимки SVG/PNG | Воспроизводимость и регрессия чертежей |
| Деплой | Docker Compose: `web+api`, `worker`, `postgres`, `caddy` (автоматический HTTPS) | Один VPS: 4 vCPU, 8 ГБ RAM, 80 ГБ диск |

### Почему не Python/Blender с самого начала
Blender даёт более красивый рендер, но добавляет второй язык и тяжёлый образ, а на сервере
без GPU он медленнее. Three.js в headless Chromium укладывается в НТ-4 (черновик ≤ 10 мин) и
позволяет показывать в браузере ту же модель, что попадает в PDF. Если качества визуализаций
не хватит для приёмки («8 из 10 заказчиков подтверждают стиль»), на этапе 9 добавим
Blender-рендер из той же модели (экспорт glTF). Модель при этом не меняется.

## 5. Пошаговый план

Работаю по принципу «сначала сквозной скелет, потом наращивание». Уже на этапе 3 будет
работать вся цепочка «анкета → бриф → проверки → модель → фасад в PDF» в упрощённом виде.
Дальше каждый модуль доводится до требований ТЗ. После каждого этапа: коммит, тесты, короткий
отчёт вам и демонстрация.

### Этап 0. Подготовка (0,5–1 день)
- Репозиторий, pnpm workspaces, TypeScript strict, ESLint/Prettier, Vitest.
- `docker-compose.dev.yml`: Postgres. Скрипты `pnpm dev`, `pnpm test`.
- CI на GitHub Actions: lint, typecheck, тесты.
- **Результат:** пустое приложение открывается в браузере, API отвечает `/health`.

### Этап 1. Нормативная база и первый профиль (ТЗ, этап 1)
- `docs/norms.md`: перечень стандартов из раздела 2 ТЗ и пометка, какие значения требуют сверки с действующей редакцией.
- Схема профиля норм и файл `profiles/ru.yaml` (СП 55.13330 + типовые значения ПЗЗ): отступы, предельная высота, процент застройки, минимальная ширина входной двери, уклоны по покрытиям, удельная стоимость м² по регионам, доли остекления по климату.
- Шаблон `profiles/_template.yaml` для новых стран (ФТ-12) и загрузчик с проверкой по схеме.
- **Результат:** профиль загружается и валидируется. Тест: добавление профиля-заглушки без правки кода.
- ⚠ Значения из СП и ПЗЗ я заполню по своим знаниям и помечу «требует сверки». Окончательные значения должен подтвердить специалист.

### Этап 2. Модель данных и сценарий анкеты (ТЗ, этап 2)
- `brief-schema`: сущности из 5.1 (project, client, site, style, massing, levels[], roof, facades[], openings[], exterior_elements[], budget, assumptions[], conflicts[]); у каждого параметра атрибуты value / unit / source / rigidity / confirmed (5.2). Экспорт `brief.schema.json`.
- Банк вопросов `questions/*.yaml` по блокам A–I: тип ответа, единицы, обязательность, условия показа (`showIf`), пояснения терминов, картинки для визуального выбора.
- Каталог стилей (≥ 12, ФТ-4): формы кровли, пропорции окон, материалы, палитры RAL/NCS, характер, параметры для генератора. Первичный список: современный минимализм, скандинавский, барнхаус, шале, фахверк, классика, неоклассика, прованс, райт / прерий, хай-тек, английский (кирпичный), средиземноморский, русский деревянный.
- Пакет `defaults`: цепочка «профиль → стиль → общая практика» с записью обоснования в assumptions[].
- **Результат:** JSON Schema, банк вопросов, каталог стилей, unit-тесты на сценарий «минимум данных» (только стиль, площадь и этажность → полный бриф через допущения).

### Этап 3. Сквозной скелет (вертикальный срез)
Упрощённая версия всей цепочки, чтобы рано проверить архитектуру:
- анкета из ~10 вопросов → бриф → проверки В-1, В-2, В-4 → прямоугольный дом с двускатной кровлей → один фасад в SVG → PDF на A3 с основной надписью;
- 3D-просмотр этой модели в браузере.
- **Результат:** демонстрация «от ответа до листа PDF». Здесь фиксируем форматы обмена между модулями.

### Этап 4. Веб-анкета и личный кабинет (ТЗ, этап 3; ФТ-1, 2, 5, 9, 16; НТ-1, 2, 3, 9)
- Регистрация и вход, проекты, версии брифа.
- Движок анкеты: ветвление, три формы ответа, отметка «жёсткий / гибкий ± %», автосохранение после каждого ответа, продолжение с места остановки.
- Визуальный выбор: стиль, кровля, окна, материалы (карточки с изображениями).
- Блок B: адрес → геокодирование → подбор профиля; ввод размеров и ориентации участка на простой схеме.
- Загрузка документов (ГПЗУ, топосъёмка, фото) → извлечение параметров через Claude API → подтверждение заказчиком (ФТ-5).
- Адаптивная вёрстка и переключатель ru/en.
- Итоговая сводка брифа на 1–2 страницы с допущениями и кнопка «Утвердить» (с датой и версией).
- **Результат:** анкета проходит на телефоне и компьютере, черновик брифа сохраняется.

### Этап 5. Стилевой анализ (М2; ФТ-3)
- Загрузка 5–10 референсов с пометками «нравится / не нравится» и уточнением «что именно».
- Claude vision извлекает признаки (форма кровли, материал, цвет, пропорции окон, этажность). Признаки агрегируются в стилевой профиль, ближайшие стили каталога ранжируются.
- Заказчик подтверждает или правит признаки.
- **Результат:** стилевой профиль в брифе (style), источник `document` или `client`.

### Этап 6. Валидация и конфликты (ТЗ, этап 4; ФТ-7, 8; М4)
- Все проверки В-1…В-13, пороги берутся только из профиля.
- Геометрические проверки: пятно застройки в отступах (В-3), раскладка проёмов по фасадам с простенками и углами (В-6), проёмы против высоты этажа (В-7), высоты (В-4, В-5).
- Для каждого конфликта ≥ 2 варианта разрешения с расчётом последствий (площадь, стоимость, облик); жёсткие параметры не меняются без согласия заказчика.
- Проверка на лету в анкете и возврат к уточняющим вопросам при блокирующих конфликтах.
- **Результат:** три обязательных противоречивых сценария из приёмки (дом больше участка, высота выше регламента, окон больше, чем вмещают фасады) находятся и доводятся до решения автотестами.

### Этап 7. Генератор внешней архитектуры (ТЗ, этап 5; ФТ-10, 11, 13; М5)
- Модель оболочки: этажи, контур плана (прямоугольник, Г, П), стены, цоколь, кровля всех форм из анкеты (плоская, односкатная, двускатная, вальмовая, сложная из комбинации), свесы, мансарда.
- Раскладка проёмов по фасадам с учётом ориентации, видов, ритма стиля, простенков; марки проёмов (О-1, Д-1…).
- Внешние элементы: крыльцо, терраса, балкон, навес, гараж, эркер.
- Материалы и цвета по стилю и брифу.
- ≥ 2 варианта: детерминированный генератор с seed = хэш(бриф, номер варианта) (НТ-5). Варианты отличаются композицией (кровля, массинг, ритм окон, материалы) в рамках стиля.
- Прослеживаемость: у каждого элемента модели ссылка на параметр брифа или допущение (НТ-6).
- Замечания к варианту → изменения брифа → новая версия → повторный цикл (ФТ-13).
- **Результат:** в кабинете показываются два варианта в 3D, заказчик выбирает или пишет замечания.

### Этап 8. Выпуск комплекта (М6; ФТ-14, 15; раздел 6)
- Визуализации: ≥ 4 ракурса с уровня глаз + вид сверху, PNG 3840×2160; черновой рендер для выбора варианта.
- Чертежи (SVG → PDF, A3, ISO): схема посадки 1:500/1:200 со стрелкой севера; 4 фасада 1:100 с размерами, отметками и материалами; план кровли 1:100; габаритная схема по этажам и схематичный разрез.
- Таблицы: ведомость окон и дверей, паспорт отделки (RAL/NCS, площади), ТЭП по ISO 9836.
- Тексты: бриф, реестр допущений, пояснительная записка (шаблон + генерация текста через Claude по данным модели), отчёт соответствия.
- Альбом: титул, содержание, номер ревизии, дата и «Концепция. Не для строительства» на каждом листе. Скачивание PDF и ZIP из кабинета.
- **Результат:** полный комплект из 10 позиций, проверка совпадения марок, количества и размеров между ведомостью, фасадами и визуализациями автотестом.

### Этап 9. Качество, скорость, безопасность
- Замер НТ-4 (вариант ≤ 10 мин, комплект ≤ 30 мин) на целевом сервере, оптимизация.
- Шифрование ПДн, удаление проекта и данных по запросу (НТ-8), журнал действий.
- Улучшение визуализаций (текстуры, окружение, при необходимости Blender).
- **Результат:** отчёт о производительности и безопасности.

### Этап 10. Испытания (ТЗ, этап 6)
- Десять тестовых сценариев-заказчиков (автотесты + ручной прогон), включая три противоречивых и «минимум данных».
- Протокол испытаний по чек-листу 8.2.

### Этап 11. Деплой и передача (ТЗ, этап 7)
- Docker-образы, `docker-compose.prod.yml`, Caddy (HTTPS), бэкапы Postgres, обновление одной командой.
- Инструкция по развёртыванию на VPS, руководства пользователя и администратора (в том числе «как добавить профиль, стиль или вопрос»).

## 6. Риски и как я их снижаю

| Риск | Мера |
|---|---|
| Качество автоматического облика («8 из 10 подтверждают стиль») — самая сложная часть | Сильные стилевые правила в каталоге, ранний показ вариантов (этап 3 и 7), итерации по отзывам |
| Значения норм РФ взяты по памяти | Помечаются «требует сверки», вынесены в конфиг, сверка специалистом до испытаний |
| Извлечение данных из сканов ГПЗУ ненадёжно | Всё извлечённое показывается на подтверждение; ручной ввод остаётся всегда |
| Рендер 4K на сервере без GPU медленный | Черновой рендер в низком разрешении для выбора варианта, финальный в фоне; Blender как запасной вариант |
| Объём ТЗ большой | Сквозной скелет на этапе 3, далее поэтапная поставка работающих частей |
