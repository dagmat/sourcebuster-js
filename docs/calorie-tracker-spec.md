# Техническое задание: семейное приложение для учёта питания «Семейный рацион»

| Параметр | Значение |
|---|---|
| Версия документа | 0.1 (черновик) |
| Дата | 03.10.2026 |
| Круг пользователей | одна семья, 2–6 человек |
| Ключевой акцент | распознавание съеденного по фото и голосу с обучением на рационе семьи |

---

## 1. Назначение и цели

### 1.1. Назначение
Приложение позволяет членам одной семьи фиксировать всё съеденное **за несколько секунд** — сфотографировав тарелку или наговорив фразу («съел две котлеты с пюре и салат»), — и на основе накопленных данных:

- считать калории, белки, жиры, углеводы (КБЖУ) и микронутриенты;
- оценивать сбалансированность рациона относительно физиологических норм;
- давать рекомендации и составлять план питания на неделю;
- контролировать соблюдение плана.

### 1.2. Главная идея
Универсальные приложения (FatSecret, MyFitnessPal и т. п.) распознают еду «вообще» и поэтому ошибаются. У одной семьи рацион **ограничен и повторяется**: обычно 50–150 блюд, одна и та же посуда, одни и те же рецепты, одни и те же магазинные продукты. Приложение должно **выучить этот замкнутый набор** и распознавать по нему, а не по всему миру. Это превращает сложную задачу «что это за еда?» в простую задачу «какое из *наших* блюд это и сколько его?».

### 1.3. Цели (измеримые)
| № | Цель | Целевое значение (после периода обучения) |
|---|---|---|
| Ц1 | Точность определения блюда (top-1) для блюд из семейного каталога | ≥ 95 % |
| Ц2 | Точность определения блюда в top-3 (выбор из подсказок одним тапом) | ≥ 99 % |
| Ц3 | Ошибка оценки массы порции (MAPE) | ≤ 15 % для фото, ≤ 10 % для голоса с указанием количества |
| Ц4 | Время записи приёма пищи от открытия приложения до сохранения | медиана ≤ 10 с |
| Ц5 | Доля записей, сохранённых без ручной правки | ≥ 85 % |
| Ц6 | Ошибка суточной калорийности относительно контрольного взвешивания | ≤ 10 % |

### 1.4. Вне рамок первой версии
- Публичная регистрация, монетизация, социальные функции.
- Медицинская диагностика и лечебные диеты (приложение — не медицинское изделие; рекомендации носят информационный характер).
- Интеграция с фитнес-трекерами (кандидат на v2, см. раздел 10).

## 2. Пользователи и роли

| Роль | Описание | Права |
|---|---|---|
| Администратор семьи | Создаёт семью, приглашает участников, управляет каталогом блюд и рецептами | Все |
| Участник | Взрослый член семьи | Свои записи, общий каталог (добавление/правка), свои цели и планы |
| Ребёнок (профиль без входа) | Записи ведёт взрослый | Записи ведутся от имени ребёнка другим участником |

**Профиль участника:** имя, пол, дата рождения, рост, вес (история), уровень физической активности, цель (снижение / поддержание / набор массы), ограничения (аллергии, непереносимости, религиозные/этические), особые состояния (беременность, лактация — влияют на нормы).

Одна запись может относиться к нескольким участникам (общий обед: «мы с дочкой съели кастрюлю супа» → распределение порций).

## 3. Ключевой функционал: распознавание съеденного

### 3.1. Общая концепция

```
 Фото / Голос / Текст
        │
        ▼
 ┌──────────────────────┐
 │ 1. Извлечение        │  фото → кандидаты блюд + оценка объёма
 │    (мультимодальная  │  голос → текст → список «что + сколько»
 │    модель / STT)     │
 └─────────┬────────────┘
           ▼
 ┌──────────────────────┐
 │ 2. Сопоставление с   │  поиск по эмбеддингам фото и названий
 │    СЕМЕЙНЫМ каталогом│  + контекст (время, кто, что готовили
 │    (retrieval)       │    сегодня, план питания)
 └─────────┬────────────┘
           ▼
 ┌──────────────────────┐
 │ 3. Оценка порции     │  известная посуда, типичные порции
 │                      │  конкретного человека, вес кастрюли
 └─────────┬────────────┘
           ▼
 ┌──────────────────────┐
 │ 4. Подтверждение     │  высокая уверенность → автосохранение
 │    пользователем     │  средняя → 1 тап выбора из top-3
 │                      │  низкая → уточняющий вопрос
 └─────────┬────────────┘
           ▼
 ┌──────────────────────┐
 │ 5. Обучение          │  каждая правка = размеченный пример
 └──────────────────────┘
```

Принцип: **модель общего назначения отвечает за «понимание», семейный каталог — за «точность»**. Финальный ответ всегда выбирается из семейного каталога (или явно помечается как новое блюдо).

### 3.2. Семейный каталог блюд (ядро системы)

Каталог — центральная сущность, на которой держится точность. Каждая запись каталога — **блюдо или продукт в том виде, в каком его ест эта семья**.

| Поле | Описание |
|---|---|
| Название + синонимы | «Мамины котлеты», «котлеты», «котлетки» — все варианты, как называют в семье |
| Тип | Домашнее блюдо по рецепту / магазинный продукт (со штрихкодом) / блюдо вне дома (кафе, столовая) / простой продукт (яблоко, хлеб) |
| Рецепт | Ингредиенты с массой (для домашних блюд), выход готового блюда, способ приготовления (учёт ужарки/уварки) |
| Пищевая ценность на 100 г | Рассчитывается из рецепта по нутриентной базе (раздел 4) или берётся с этикетки |
| Типичные порции | «1 котлета ≈ 85 г», «тарелка супа ≈ 350 г», «половник ≈ 120 г» — свои для каждого блюда |
| Эталонные фото | Набор фото этого блюда, накопленный из подтверждённых записей (эмбеддинги хранятся для поиска) |
| Визуальные признаки | Текстовое описание для модели («светло-коричневые овальные, подаются с зеленью») |
| Статистика | Частота, типичное время приёма, кто обычно ест, сезонность |
| Варианты | «Котлеты куриные» / «котлеты говяжьи» — похожие визуально, но разные по составу |

**Варианты блюд и партии приготовления.** Если сегодня сварили борщ, создаётся «партия»: конкретная кастрюля с известным составом (по рецепту или с отклонениями: «в этот раз без мяса»). Пока партия не закончилась, любое «съел борщ» с высоким приоритетом сопоставляется с ней. Опционально — взвешивание кастрюли до и после для точного расчёта.

### 3.3. Каталог посуды (калибровка порций по фото)
- Пользователь один раз фотографирует свои тарелки, миски, кружки, указывая диаметр/объём (или фотографирует рядом с банковской картой как эталоном размера).
- Модель распознаёт посуду на фото и использует её как масштаб для оценки объёма еды.
- Для каждой посуды хранится «полная порция» по типам блюд (полная миска супа = 400 мл).

### 3.4. Распознавание по фото

**Сценарий:**
1. Пользователь открывает приложение → сразу камера (1 тап до съёмки).
2. Фото отправляется на распознавание; во время обработки (цель ≤ 3 с) показывается превью.
3. На фото выделяются области (сегментация): каждый объект — блюдо из каталога с массой.
4. Пользователь видит карточку: «Котлета куриная ×2 (170 г), Пюре (180 г), Огурец (60 г) — 520 ккал». Подтверждает или правит.

**Требования:**
- Несколько блюд на одном фото (тарелка с гарниром, стол целиком).
- Режим «до и после»: фото полной тарелки и остатков — масса съеденного = разница.
- Распознавание упаковки/этикетки: штрихкод (сканер) и OCR состава и КБЖУ с этикетки.
- Определение «кто ест» по умолчанию — владелец телефона; можно переключить.
- Фото без еды или нечёткое → просьба переснять, а не случайная догадка.
- Работа при плохом интернете: фото ставится в очередь, распознаётся при появлении сети; запись можно сохранить «черновиком».

**Подход к реализации (рекомендуемый):**
- **Этап извлечения:** мультимодальная LLM через API (например, Claude) получает фото + **короткий список кандидатов из семейного каталога** (top-20 по визуальному сходству и контексту) + описание известной посуды. Модель возвращает структурированный JSON: блюда, ссылки на ID каталога или «новое», оценка объёма/массы, уверенность.
- **Визуальный поиск:** эмбеддинги изображений (CLIP/SigLIP-подобная модель) для каждого подтверждённого фото; поиск ближайших соседей по эталонным фото каталога. На небольшом каталоге это даёт очень высокую точность без обучения собственной нейросети.
- **Контекст как признак:** время суток, день недели, кто снимает, какие партии блюд сейчас «открыты», что стоит в плане питания на этот приём пищи. Блюдо из плана получает повышенный вес.
- **Дообучение (опционально, после накопления ≥ 30 фото на блюдо):** лёгкий классификатор поверх эмбеддингов (логистическая регрессия / kNN) для каталожных блюд — быстрый и дешёвый, может работать на сервере семьи или даже на устройстве.

### 3.5. Распознавание по голосу

**Сценарий:**
1. Кнопка-микрофон на главном экране / виджет / голосовой ассистент телефона («Окей, запиши в рацион…»).
2. Пользователь говорит в свободной форме: «На обед тарелка борща со сметаной, кусок чёрного хлеба и компот».
3. Система показывает разбор: «Борщ (партия от 02.10) — 350 г; Сметана 15 % — 20 г; Хлеб бородинский — 35 г; Компот — 250 мл». Подтверждение одним тапом.

**Требования:**
- Свободная разговорная речь на русском, включая уменьшительные формы, семейные названия («мамин салат»), числительные словами, приблизительные меры («пара ложек», «полтарелки», «горсть»).
- Указание времени и человека в фразе: «вчера вечером Маша съела два йогурта».
- Добавление к фото: голосовая подпись к снимку уточняет то, чего не видно («в салате майонез», «котлеты из индейки»).
- Многошаговое уточнение: если неоднозначно — короткий вопрос голосом или кнопками («Борщ с мясом или постный?»).
- Исправление голосом: «нет, не две, а три котлеты».

**Подход к реализации:**
- **Распознавание речи (STT):** Whisper-класс модели или облачный STT с поддержкой русского языка; словарь подсказок (hotwords) из названий семейного каталога для повышения точности на «своих» словах.
- **Разбор:** LLM преобразует текст в структуру `[{что, количество, единица, кто, когда, модификаторы}]`, получая на вход список названий и синонимов каталога и словарь семейных мер («кружка» = 300 мл, «тарелка» = посуда №2).
- **Сопоставление:** нечёткий поиск по названиям и синонимам + семантический поиск по эмбеддингам текста; при равенстве — приоритет по частоте и контексту.

### 3.6. Уверенность и подтверждение

| Уровень уверенности | Поведение |
|---|---|
| Высокий (≥ 0,9 по блюду и порции) | Запись сохраняется сразу, показывается уведомление с кнопкой «Исправить» (отмена в течение 30 с или правка позже) |
| Средний (0,6–0,9) | Показываются top-3 варианта, выбор одним тапом |
| Низкий (< 0,6) или новое блюдо | Уточняющий вопрос / предложение создать новое блюдо в каталоге |

Пороги настраиваются; уверенность калибруется по истории подтверждений (если «0,9» на практике верно в 80 % случаев — порог сдвигается).

### 3.7. Обучение на рационе семьи

**Фаза 1 — «Знакомство» (первые 2–4 недели).**
- Цель: заполнить каталог 80 % реально употребляемых блюд.
- Мастер первичной настройки: выбор типичных блюд из списка популярных, ввод любимых домашних рецептов (можно голосом или фото рукописного рецепта), съёмка посуды.
- Каждая запись подробно подтверждается; приложение активно задаёт вопросы («Это новое блюдо. Как вы его называете? Это по рецепту или из магазина?»).
- Сканирование чеков из магазинов (ФНС-QR / фото чека) как источник списка покупаемых продуктов — опционально, ускоряет наполнение каталога.

**Фаза 2 — «Рабочий режим».**
- Каждое подтверждение/исправление пополняет эталонные фото и синонимы.
- Исправления сохраняются как размеченные примеры (что предложила система → что оказалось верным) — используются для пересчёта порогов и типичных порций.
- Персональные типичные порции: если папа всегда ест 3 котлеты, а дочь 1 — это становится значением по умолчанию для конкретного человека.

**Фаза 3 — «Активное обучение» (фоновое).**
- Раз в неделю — отчёт качества: какие блюда чаще всего путались, предложение разделить/слить блюда каталога («„Котлеты" и „Тефтели" путаются в 30 % случаев — это одно блюдо?»).
- Предложение досъёмки блюд, по которым мало эталонов.
- Опциональные «контрольные взвешивания» (кухонные весы) для калибровки оценки массы по фото.

**Метрики качества распознавания** (собираются автоматически, видны администратору):
- доля автоподтверждённых записей, доля исправлений;
- точность top-1 / top-3 по блюдам;
- средняя ошибка массы (по записям с контрольным взвешиванием);
- среднее время записи.

### 3.8. Прочие способы ввода
- Повтор: «как вчера на завтрак», избранные наборы («мой обычный завтрак»).
- Сканирование штрихкода.
- Текстовый ввод с автодополнением из каталога.
- Быстрый ввод воды и напитков.
- Ввод из плана питания: «съел по плану» — одним тапом.

## 4. Нутриентная база данных

### 4.1. Источники данных

| Источник | Что даёт | Применение |
|---|---|---|
| **USDA FoodData Central** (открытые данные, API) | Самая полная база: 150+ нутриентов, включая витамины, минералы, аминокислоты, жирные кислоты | Основной источник микронутриентов для базовых продуктов |
| **Таблицы химического состава российских пищевых продуктов** (Скурихин, Тутельян; база ФИЦ питания и биотехнологии) | Состав продуктов, характерных для российской кухни | Приоритетный источник для локальных продуктов (гречка, творог, кефир, ряженка и т. п.) |
| **Open Food Facts** (открытая база, API, штрихкоды) | Магазинные продукты со штрихкодами, КБЖУ с этикеток, состав | Магазинные продукты |
| **CIQUAL (Франция), McCance & Widdowson (Великобритания)** | Дополнительные открытые таблицы | Заполнение пробелов в микронутриентах |
| **Этикетка продукта** (OCR) | Фактические КБЖУ конкретного продукта | Приоритет над справочниками для КБЖУ |

### 4.2. Требования к базе
- Единая внутренняя модель нутриентов (минимум: энергия, белки, жиры (в т. ч. насыщенные, ω-3, ω-6), углеводы (в т. ч. сахара, пищевые волокна), натрий/соль, калий, кальций, магний, фосфор, железо, цинк, йод, селен, витамины A, D, E, K, C, B1, B2, B3, B5, B6, B9, B12, холестерин).
- Сопоставление продуктов разных источников (маппинг «творог 5 %» ↔ записи USDA/Скурихина) с указанием источника и качества данных для каждого значения.
- Учёт кулинарной обработки: коэффициенты потерь массы (уварка, ужарка) и потерь витаминов при термообработке (таблицы коэффициентов сохранности, USDA Retention Factors).
- Пометка «нет данных» отличается от нуля; в отчётах показывается полнота данных («данные по йоду есть для 60 % съеденного»).
- Расчёт состава домашних блюд из рецепта автоматически; при изменении рецепта — пересчёт.
- Периодическое обновление справочников (раз в квартал, полуавтоматически).

## 5. Анализ сбалансированности рациона

### 5.1. Нормы
- Базовый источник норм: **МР 2.3.1.0253-21 «Нормы физиологических потребностей в энергии и пищевых веществах для различных групп населения РФ»**; дополнительно — рекомендации ВОЗ / EFSA для показателей, отсутствующих в МР.
- Индивидуальные нормы рассчитываются по профилю: пол, возраст, масса, рост, активность, цель, беременность/лактация.
- Энергия: основной обмен (формула Миффлина — Сан Жеора) × коэффициент активности ± коррекция под цель.
- Возможность ручной корректировки норм (например, по рекомендации врача).

### 5.2. Отчёты
| Отчёт | Содержание |
|---|---|
| Дневной | Калории и БЖУ (факт/норма), распределение по приёмам пищи, вода |
| Недельный | Среднее и динамика по калориям и БЖУ; «светофор» по микронутриентам (дефицит < 70 % нормы / норма / избыток выше верхнего допустимого уровня) |
| Месячный | Устойчивые дефициты и избытки, главные «источники» каждого нутриента («80 % натрия — из колбасы и хлеба»), динамика веса |
| Семейный | Сводка по всем участникам; общие проблемы рациона семьи («у всех недобор клетчатки и витамина D») |
| Качество рациона | Разнообразие (число разных продуктов за неделю), доля овощей/фруктов, доля ультрапереработанных продуктов, сахар, соль |

Микронутриенты анализируются **за неделю и более**, а не за день (дневные колебания нормальны).

### 5.3. Рекомендации
- Конкретные и привязанные к семейному каталогу: не «ешьте больше магния», а «добавьте гречку 2 раза в неделю вместо макарон — закроет 30 % дефицита магния; это блюдо вы уже готовите».
- Приоритизация: показывать 1–3 главные рекомендации, а не список из 20.
- Учёт аллергий и ограничений каждого участника.
- Оговорка в интерфейсе: рекомендации не являются медицинскими.
- Генерация текста рекомендаций — LLM на основе рассчитанных дефицитов (числа считает детерминированный код, LLM только формулирует и подбирает блюда).

## 6. Планирование питания и контроль соблюдения

### 6.1. Недельный план
- Автоматическое составление плана на неделю для семьи с учётом: индивидуальных норм, выявленных дефицитов, предпочтений (частотные блюда из каталога), ограничений, разнообразия, бюджета времени на готовку (опционально).
- Предпочтение блюд из семейного каталога; новые блюда предлагаются дозированно (например, не более 2–3 в неделю) с рецептом.
- Учёт «партий»: одно приготовленное блюдо (кастрюля супа) распределяется на несколько приёмов пищи и участников.
- Ручное редактирование: перетаскивание блюд, замена с подсказкой равноценной альтернативы по нутриентам.
- **Список покупок**, сформированный из плана, с учётом количества членов семьи; группировка по отделам магазина; экспорт/шаринг.
- Подход к реализации: подбор плана — оптимизационная задача (целочисленное программирование / эвристический поиск по каталогу с ограничениями по нутриентам); LLM — для объяснения плана и учёта пожеланий в свободной форме («на этой неделе без рыбы, в среду гости»).

### 6.2. Контроль соблюдения
- Каждая запись о еде автоматически сопоставляется с запланированным приёмом пищи (по времени и блюду).
- Статусы приёма пищи: выполнен по плану / заменён / пропущен / сверх плана.
- Метрики: % соблюдения плана по приёмам пищи, отклонение по калориям и БЖУ от плана, «незапланированные» перекусы.
- Напоминания: о приёме пищи по плану, о том, что пора готовить (за N часов), об отсутствии записей («Обед не записан — записать?»).
- Еженедельный разбор: что соблюдалось, что нет, почему (типичные замены), автоматическая корректировка следующего плана (если план систематически не соблюдается в обед по будням — упростить будничные обеды).

## 7. Нефункциональные требования

### 7.1. Платформы
- Мобильное приложение iOS и Android (рекомендуется кроссплатформенная разработка: Flutter или React Native) — основной канал.
- Веб-интерфейс (минимальный) для администратора: каталог, рецепты, отчёты, план.
- Виджет на главный экран и быстрый вызов голосовой записи.

### 7.2. Производительность
- Распознавание фото: ≤ 3 с (p90 ≤ 5 с) при нормальной сети.
- Распознавание голоса: ≤ 2 с после окончания фразы.
- Офлайн-режим: запись черновиков, просмотр каталога, плана и отчётов; синхронизация при появлении сети.

### 7.3. Приватность и безопасность
- Данные — персональные, в т. ч. о здоровье: хранение на сервере, контролируемом семьёй (VPS или домашний сервер), либо в облаке с шифрованием.
- Фото еды по умолчанию хранятся (нужны для обучения), с возможностью удаления и настройкой срока хранения.
- При использовании внешних AI-API: передаются только фото еды и текст фразы, без профиля здоровья; провайдер с политикой неиспользования данных для обучения.
- Аутентификация: вход по ссылке-приглашению + биометрия/ПИН на устройстве.
- Резервное копирование БД ежедневно; экспорт всех данных (JSON/CSV).

### 7.4. Стоимость эксплуатации
- Ориентир: ≤ 15–30 $ в месяц на семью (хостинг + AI-API).
- Ограничение стоимости: кэширование, использование дешёвой модели для простых случаев (высокое сходство с эталоном → ответ без вызова LLM), дорогой — только для сложных.

### 7.5. Удобство
- Запись приёма пищи — максимум 2 действия в типичном случае.
- Интерфейс на русском языке; крупные элементы, тёмная тема.
- Отчёты понятны без знания нутрициологии.

                     └──────────────────────────────────────────────────────────────────┘

### 8.1. Основные сущности данных
- `Family`, `Member` (профиль, нормы, история веса)
- `Dish` (каталог: тип, синонимы, рецепт, нутриенты на 100 г, типичные порции, варианты)
- `DishPhoto` (фото + эмбеддинг + подтверждённая разметка)
- `Ingredient` / `FoodItem` (продукт нутриентной базы, источник, значения нутриентов)
- `Recipe`, `RecipeIngredient`
- `Batch` (партия приготовленного блюда: дата, фактический состав, масса, остаток)
- `Dishware` (посуда: тип, размеры, объём)
- `MealEntry` (приём пищи: участник, время, источник ввода, исходное фото/аудио/текст)
- `MealItem` (блюдо, масса, уверенность, предложено системой / исправлено пользователем)
- `RecognitionFeedback` (предсказание vs. итог — датасет для обучения)
- `MealPlan`, `PlannedMeal`, `ShoppingList`
- `NutrientNorm` (нормы по группам + индивидуальные корректировки)

## 9. Этапы разработки

| Этап | Содержание | Ориентировочно |
|---|---|---|
| **0. Прототип распознавания** | Проверка гипотезы: фото/голос → JSON с блюдами по маленькому тестовому каталогу (20 блюд семьи); замер точности на 200 реальных снимках | 2–3 недели |
| **1. MVP записи** | Мобильное приложение: профили, каталог, рецепты, запись по фото/голосу/штрихкоду с подтверждением, расчёт КБЖУ, дневной отчёт, сбор обратной связи | 6–8 недель |
| **2. Обучение и точность** | Эталонные фото и векторный поиск, партии блюд, каталог посуды, персональные порции, отчёт качества распознавания, калибровка порогов | 4–6 недель |
| **3. Нутриентная аналитика** | Импорт USDA/Скурихин/OFF, микронутриенты, нормы МР 2.3.1.0253-21, недельные/месячные отчёты, рекомендации | 4–6 недель |
| **4. Планирование** | Недельный план, список покупок, контроль соблюдения, напоминания, недельный разбор | 4–6 недель |

**Критерий приёмки этапа 2** (главный для проекта): после 4 недель использования семьёй выполняются цели Ц1–Ц5 из п. 1.3 на выборке за последнюю неделю.
