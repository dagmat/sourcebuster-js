# 01. Серверная часть

[← к оглавлению](README.md)

## 1. Общая схема

Система — клиент-серверная. **Сервер семьи** хранит все данные, выполняет распознавание, расчёты, аналитику и планирование. **Клиенты** (мобильные приложения всех членов семьи и веб-кабинет) — тонкие в смысле логики, но с офлайн-кэшем: могут записывать еду без сети и синхронизироваться позже.

```
        │                 │                 │                     │
```

## 2. Технологический стек (рекомендуемый)

| Компонент | Выбор | Обоснование |
|---|---|---|
| Язык сервера | Python 3.12 | Экосистема ML и работы с данными |
| Веб-фреймворк | FastAPI + Pydantic | Асинхронность, автоматическая OpenAPI-спецификация, строгая валидация |
| БД | PostgreSQL 16 + расширение pgvector | Реляционные данные и векторный поиск в одной БД; для семьи (десятки тысяч векторов) отдельная векторная БД не нужна |
| Миграции | Alembic | Стандарт для SQLAlchemy |

| Мониторинг | Prometheus-метрики + Grafana (опционально), Sentry для ошибок | |

## 3. Модель развёртывания

### 3.1. Варианты размещения

| Вариант | Плюсы | Минусы | Рекомендация |
|---|---|---|---|
| **VPS** (облачный сервер) | Доступен из любой сети, стабильный канал, простой TLS | Абонентская плата (~5–15 $/мес) | **Основной** |
| Домашний сервер / NAS | Данные дома, нет абонентской платы | Нужен белый IP или туннель (Cloudflare Tunnel, Tailscale), зависимость от домашнего интернета и питания | Альтернатива |
| Полностью локальный (без внешних AI-API) | Максимальная приватность | Нужен GPU для локальной мультимодальной модели, точность ниже | Только по требованию |

### 3.2. Требования к серверу
- Минимум: 2 vCPU, 4 ГБ RAM, 40 ГБ SSD.
- Рекомендуется: 4 vCPU, 8 ГБ RAM (локальные эмбеддинги + оптимизатор плана без задержек).
- Объём данных: ~15 фото/день × 300 КБ (после сжатия) ≈ 1,6 ГБ/год; аудио ≈ 0,3 ГБ/год; БД < 2 ГБ/год.

### 3.3. Состав контейнеров (docker-compose)

| Контейнер | Назначение |
|---|---|
| `proxy` | Caddy: TLS, маршрутизация `/api`, `/ws`, `/admin` |
| `api` | FastAPI (2–4 процесса uvicorn) |
| `worker-fast` | Очередь `recognition` — задачи, ожидаемые пользователем (приоритет, 2–4 параллельные задачи) |
| `worker-bg` | Очереди `embeddings`, `analytics`, `planning`, `maintenance`, `import` |
| `scheduler` | Периодические задачи (cron внутри arq) |
| `embedder` | Сервис эмбеддингов (HTTP/gRPC, ONNX Runtime) |
| `postgres` | БД |
| `redis` | Очереди, pub/sub, кэш |
| `minio` | Хранилище файлов |
| `backup` | Ежедневное резервное копирование |

### 3.4. Первичная установка
1. Администратор арендует VPS, указывает домен (или получает бесплатный поддомен).
2. Запускает установочный скрипт: `curl … | sh` → скачивается `docker-compose.yml`, генерируются секреты (`.env`), поднимаются контейнеры, применяются миграции, загружаются справочники нутриентов (раздел 9).
3. Скрипт выводит **одноразовую ссылку и QR-код** создания семьи и первого администратора.
4. Администратор открывает ссылку в приложении → создаётся семья и учётная запись → устройство администратора подключено.
5. В веб-кабинете администратор вводит ключи внешних AI-API и месячный лимит расходов.

Обновление: `./update.sh` — скачивает новые образы, делает резервную копию БД, применяет миграции, перезапускает. Откат — восстановление из копии, сделанной перед обновлением.

## 4. Подключение устройств и аутентификация

### 4.1. Модель
- **Семья** (`family`) — единица изоляции данных. Сервер рассчитан на одну семью, но все таблицы содержат `family_id` (возможность обслуживать родственников на том же сервере без переделки).
- **Участник** (`member`) — человек. Может не иметь устройств (ребёнок).
- **Учётная запись** (`account`) — вход; привязана к участнику.
- **Устройство** (`device`) — конкретный экземпляр приложения; принадлежит учётной записи. У одной учётной записи может быть несколько устройств (телефон + планшет).
- **Общее устройство** (кухонный планшет) — привязано к семье, а не к человеку; при записи нужно выбрать участника (по умолчанию — «вся семья / распределить»).

### 4.2. Подключение нового устройства (сопряжение)

```
Администратор (веб/приложение)          Сервер                     Новое устройство
        │ «Добавить участника/устройство»  │                              │
        │─────────────────────────────────▶│ создаёт invite: код 128 бит,│
        │                                  │ TTL 24 ч, одноразовый,      │
        │                                  │ роль, участник              │
        │◀───── QR-код / ссылка ───────────│                              │
        │                                  │                              │
        │                     (показывает QR)  ─────────────────────────▶ │ сканирует
        │                                  │◀── POST /auth/redeem-invite ─│ {code, device_info,
        │                                  │                              │  device_public_key}
        │                                  │ проверяет код, создаёт       │
        │                                  │ account (если новый) и device│
        │                                  │── access + refresh токены ──▶│
        │                                  │                              │ устанавливает ПИН/биометрию
        │                                  │                              │ локально; полная начальная
        │                                  │◀── GET /sync/bootstrap ──────│ синхронизация
```

- Пароли не используются: вход только через приглашение (для веб-кабинета — вход подтверждается с уже подключённого телефона по QR, как в мессенджерах).
- Ссылка-приглашение содержит адрес сервера, поэтому пользователю не нужно ничего вводить вручную.

### 4.3. Токены
| Токен | Срок | Хранение на клиенте | Назначение |
|---|---|---|---|
| Access (JWT, подпись Ed25519) | 15 мин | В памяти | Авторизация запросов; содержит `account_id`, `member_id`, `device_id`, `family_id`, `role` |
| Refresh (случайный, 256 бит) | 90 дней, скользящий | Защищённое хранилище ОС (Keychain / Android Keystore) | Получение нового access; **ротация при каждом использовании**; повторное использование старого refresh → отзыв всех токенов устройства (защита от кражи) |

- Администратор видит список устройств (модель, последний вход, IP) и может **отключить устройство** — его refresh-токены отзываются, при следующем запросе устройство получает 401 и очищает локальные данные.
- На устройстве — ПИН/биометрия для открытия приложения (локальная защита, не серверная).

### 4.4. Авторизация (права)
Проверяется на сервере для каждого запроса по матрице «роль × ресурс × действие». Примеры:

| Действие | Администратор | Взрослый | Ограниченный |
|---|---|---|---|
| Создать запись о еде за себя | ✔ | ✔ | ✔ |
| Создать запись за другого участника | ✔ | ✔ (за детей и с разрешения участника) | ✘ |
| Редактировать каталог | ✔ | ✔ | только предлагать |
| Видеть вес и отчёты другого участника | ✔ | если разрешено | ✘ |
| Управлять устройствами, ключами API, бэкапами | ✔ | ✘ | ✘ |

## 5. Синхронизация данных между устройствами

### 5.1. Требования
- Запись о еде должна сохраняться **мгновенно**, даже без сети (в самолёте, в подвале кафе).
- Изменения с одного устройства появляются на остальных за ≤ 5 с при наличии сети.
- Никакие данные не теряются при конфликтах.

### 5.2. Подход: offline-first с журналом изменений
1. **Идентификаторы генерирует клиент** — UUIDv7 (сортируемые по времени). Запись создаётся локально с готовым ID, поэтому нет «временных» ID и пересопоставления.
2. **Исходящий журнал (outbox) на клиенте.** Каждое изменение — операция `{op_id, entity, entity_id, type: create|update|delete, fields, base_version, client_ts}`. Операции отправляются пакетами.
3. **Сервер — авторитетный.** Каждое принятое изменение увеличивает глобальный счётчик семьи `change_seq` и пишется в таблицу `change_log` (`seq, entity, entity_id, op, changed_fields, author_device`).
4. **Получение изменений:** клиент хранит последний полученный `seq` и запрашивает `GET /sync/pull?since=<seq>` (пакетами до 500). Дополнительно сервер шлёт по WebSocket уведомление «есть изменения до seq N» — клиент сразу делает pull.
5. **Идемпотентность:** `op_id` уникален; повторная отправка той же операции (после обрыва сети) не создаёт дублей.

### 5.3. Разрешение конфликтов по типам сущностей

| Сущность | Стратегия | Пояснение |
|---|---|---|
| Приём пищи, позиции | Владелец + «последний пишущий побеждает» по полю | Обычно запись правит только автор; если два устройства правили разные поля — объединяются; одно поле — побеждает более позднее по серверному времени, проигравшая версия сохраняется в истории |
| Блюдо каталога, рецепт | Версионирование | Каждое изменение рецепта создаёт новую версию; записи о еде ссылаются на версию, действовавшую на момент еды (пересчёт истории не происходит без явного запроса) |
| Партия (остаток) | Журнал событий | Остаток не хранится как редактируемое число: он вычисляется как `начальная масса − Σ съеденного − Σ списаний`. Два устройства, одновременно записавшие «ели суп», не конфликтуют |
| Профиль, цели | «Последний пишущий побеждает» | Редкие изменения |
| План питания | Блокировка на редактирование недели (мягкая, 5 мин) + версия | Предотвращает одновременную перестройку плана двумя людьми |
| Удаление | «Надгробие» (soft delete, `deleted_at`) | Удалённые записи передаются клиентам как удалённые; физическая очистка — через 90 дней |

### 5.4. Начальная синхронизация (bootstrap)
Новое устройство получает: профиль семьи, участников, каталог (без эталонных фото — только миниатюры по запросу), рецепты, посуду, открытые партии, план на текущую и следующую недели, записи о еде за последние 30 дней, текущий `change_seq`. Более старая история подгружается по требованию (при прокрутке).

### 5.5. Медиафайлы
- Фото сжимается на клиенте (длинная сторона 1600 px, JPEG/WebP q≈80, ~200–400 КБ), удаляются EXIF-геоданные.
- Загрузка: `POST /media/upload-url` → сервер выдаёт подписанный URL MinIO (срок 10 мин) → клиент загружает напрямую → `POST /media/{id}/complete`. Для слабых сетей — возобновляемая загрузка частями.
- Сервер создаёт миниатюры (256 px) и хранит оригинал. Доступ к файлам — только через подписанные URL с коротким сроком.

## 6. API (основные группы)

Все эндпоинты — REST/JSON под `/api/v1`, спецификация OpenAPI генерируется автоматически и является частью приёмки. Real-time — WebSocket `/ws`.

| Группа | Ключевые эндпоинты |
|---|---|
| Auth | `POST /auth/redeem-invite`, `POST /auth/refresh`, `POST /auth/web-login/qr`, `DELETE /devices/{id}` |
| Семья | `GET/PATCH /family`, `GET/POST/PATCH /members`, `POST /invites` |
| Синхронизация | `POST /sync/push` (пакет операций), `GET /sync/pull?since=`, `GET /sync/bootstrap` |
| Медиа | `POST /media/upload-url`, `POST /media/{id}/complete`, `GET /media/{id}` (редирект на подписанный URL) |
| Распознавание | `POST /recognition/jobs` (фото/аудио/текст + контекст), `GET /recognition/jobs/{id}`, `POST /recognition/jobs/{id}/feedback` |
| Приёмы пищи | `GET/POST/PATCH/DELETE /meals`, `POST /meals/{id}/split` (распределение общего приёма), `POST /meals/repeat` |
| Каталог | `GET/POST/PATCH /dishes`, `POST /dishes/{id}/merge`, `GET /dishes/search?q=`, `GET/POST /recipes`, `GET/POST /dishware`, `GET /barcode/{code}` |
| Партии | `POST /batches`, `POST /batches/{id}/weigh`, `POST /batches/{id}/close` |
| Нутриенты | `GET /foods/search`, `GET /foods/{id}`, `GET /norms/{member_id}` |
| Аналитика | `GET /reports/daily`, `/weekly`, `/monthly`, `/family`, `GET /recommendations` |
| План | `POST /plans/generate`, `GET/PATCH /plans/{week}`, `GET /plans/{week}/shopping-list`, `GET /plans/{week}/adherence` |
| Качество распознавания | `GET /quality/metrics`, `GET /quality/confusions`, `GET /quality/suggestions` |
| Админ | `GET/PUT /admin/ai-settings`, `GET /admin/costs`, `POST /admin/backup`, `GET /admin/health` |

### 6.1. Пример: создание задачи распознавания

```json

    "audio": null,
    "text": null
```

### 6.2. WebSocket-события

| Событие | Кому | Когда |
|---|---|---|
| `sync.changed {seq}` | Всем устройствам семьи | Принято любое изменение |
| `recognition.progress {job_id, stage}` | Устройству-инициатору | Этапы: `uploaded`, `analyzing`, `matching`, `done` |
| `recognition.completed` | Устройству-инициатору | Результат готов |
| `batch.low {batch_id}` | Всем | Партия почти закончилась |
| `plan.updated {week}` | Всем | План изменён |
| `notify {type, payload}` | Адресату | Напоминания, отчёты |

Если устройство не в сети по WebSocket — важные события дублируются push-уведомлением через FCM/APNs (только заголовок без данных о питании; данные устройство забирает при синхронизации).

## 7. Серверные сервисы (модули) и их логика

Сервер — модульный монолит: один кодовый проект, модули с явными границами (отдельные пакеты Python, взаимодействие через интерфейсы сервисного слоя). Микросервисы для семейного масштаба избыточны.

### 7.1. Модуль «Записи о еде» (Meals)
- Создание/изменение/удаление приёмов пищи и позиций; валидация (масса > 0, время не в будущем более чем на 1 ч, участник принадлежит семье).
- При сохранении позиции: **фиксирует нутриенты** — копирует значения на 100 г из версии блюда на момент записи (снимок), чтобы последующие правки рецепта не меняли историю незаметно.
- При ссылке на партию — создаёт событие расхода партии.
- Распределение общего приёма пищи между участниками (алгоритм — [02-recognition.md](02-recognition.md), раздел 6.5).
- Публикует доменные события `meal.created/updated/deleted` во внутреннюю шину (Redis Streams) — их слушают аналитика, обучение и контроль плана.

### 7.2. Модуль «Каталог»
- CRUD блюд, вариантов, синонимов, рецептов (с версиями), посуды, типичных порций.
- Поиск: полнотекстовый (PostgreSQL `tsvector` с русской морфологией) + триграммный (`pg_trgm`, опечатки) + семантический (текстовые эмбеддинги).
- Слияние блюд (merge): все записи, эталонные фото, синонимы переносятся на целевое блюдо; исходное помечается как слитое (редирект ID).
- Разделение блюда (split): выбранные эталонные фото и записи переносятся в новое блюдо.

### 7.3. Модуль «Распознавание»
- Принимает задачи, ставит в очередь `recognition`, оркестрирует этапы (подробно — [02-recognition.md](02-recognition.md)).
- Хранит все промежуточные данные задачи (кандидаты, сырой ответ модели, итоговые гипотезы, время этапов) — для отладки и обучения.
- Принимает обратную связь (что пользователь подтвердил/исправил) и сохраняет в `recognition_feedback`.

### 7.4. Модуль «Обучение» (Learning)
Слушает события подтверждений и выполняет периодические задачи (раздел 8). Обновляет: эталонные фото, синонимы, типичные порции, контекстные приоры, веса модели ранжирования, калибровку уверенности.

### 7.5. Модуль «Нутриенты»
Справочник продуктов, расчёт состава рецептов, нормы участников — [03-nutrition.md](03-nutrition.md).

### 7.6. Модуль «Аналитика и рекомендации»
Агрегаты по дням/неделям, отчёты, поиск дефицитов, генерация рекомендаций. Агрегаты пересчитываются инкрементально по событиям `meal.*` (дневной агрегат участника пересчитывается целиком при любом изменении записей этого дня — это дешево).

### 7.7. Модуль «Планирование»
Генерация плана, список покупок, сопоставление факта с планом — [04-planning.md](04-planning.md).

### 7.8. Модуль «Уведомления»
- Расписание напоминаний для каждого участника (с учётом часового пояса и «тихих часов»).
- Каналы: WebSocket, push (FCM/APNs), в будущем — Telegram-бот.
- Дедупликация: не напоминать о приёме пищи, если запись уже есть.

### 7.9. AI-шлюз
Единая точка вызова внешних моделей. Все модули обращаются к моделям **только** через него.

| Функция | Описание |
|---|---|
| Абстракция провайдеров | Интерфейсы `vision_extract()`, `parse_speech()`, `transcribe()`, `generate_text()`; провайдер и модель задаются в настройках |
| Версии промптов | Промпты хранятся в репозитории как шаблоны с версией; в каждой задаче фиксируется версия промпта и модели |
| Структурированный вывод | Ответ модели валидируется по JSON-схеме; при невалидном ответе — 1 повтор с сообщением об ошибке, затем — запасная модель |
| Повторы и таймауты | Таймаут 8 с для распознавания; экспоненциальная задержка; circuit breaker при серии ошибок провайдера |
| Запасной путь | Если внешний API недоступен — распознавание только по эмбеддингам и контексту (точность ниже, решение `pick_from_top3` или `ask`); голос — через локальный STT |
| Учёт стоимости | Токены и стоимость каждого вызова → таблица `ai_usage`; дневной/месячный лимит; при 80 % лимита — уведомление администратору; при 100 % — переключение на дешёвую модель или только локальный путь |
| Кэш | Идентичные запросы (хэш входа + версия промпта) не повторяются |
| Приватность | В запрос не передаются имена, вес, нормы, здоровье; только фото, текст фразы и список названий блюд-кандидатов |

### 7.10. Сервис эмбеддингов
- Отдельный контейнер с моделью изображений (SigLIP/CLIP, ONNX) и текстовой моделью (многоязычная, поддерживающая русский).
- API: `POST /embed/image` (изображение или фрагмент → вектор 768), `POST /embed/text`.
- Версия модели хранится с каждым вектором. При смене модели — фоновая переиндексация всех эталонных фото, поиск идёт по старой версии до завершения.

## 8. Фоновые и периодические задачи

| Задача | Расписание | Что делает |
|---|---|---|
| `recognize` | По событию | Конвейер распознавания (приоритетная очередь) |
| `embed_reference` | По подтверждению записи | Вырезает фрагмент фото по области позиции, считает эмбеддинг, добавляет в эталоны блюда (с дедупликацией) |
| `update_priors` | По подтверждению + ночью полный пересчёт | Контекстные вероятности блюд |
| `update_portions` | По подтверждению | Типичные порции участник × блюдо |
| `recalibrate` | Ночью, 03:00 | Переобучение весов ранжирования и калибровки уверенности, пересчёт порогов |
| `quality_report` | Ночью | Метрики качества, матрица путаницы, предложения слить/разделить блюда, список блюд с малым числом эталонов |
| `daily_aggregates` | По событию + ночью сверка | Дневные суммы нутриентов |
| `weekly_report` | Воскресенье, 19:00 | Недельные отчёты, рекомендации, разбор соблюдения плана |
| `plan_draft` | Суббота, 10:00 (настраивается) | Черновик плана на следующую неделю |
| `batch_expiry` | Каждый час | Закрытие партий с истёкшим сроком хранения (с вопросом владельцу) |
| `reminders` | Каждые 5 мин | Отправка запланированных напоминаний |
| `reference_import` | Раз в квартал / вручную | Обновление справочников нутриентов |
| `backup` | Ежедневно, 04:00 | Резервная копия БД и медиа |
| `cleanup` | Еженедельно | Очистка «надгробий» старше 90 дней, сирот-медиа, логов |

Требования к задачам: идемпотентность (повторный запуск не портит данные), блокировка от параллельного запуска одной периодической задачи (Redis lock), повтор с задержкой при ошибке (до 5 раз), «мёртвая очередь» для окончательно упавших задач с отображением в админке.

## 9. Хранение данных

### 9.1. PostgreSQL
- Все бизнес-данные, эмбеддинги (pgvector, индекс HNSW, косинусное расстояние), журнал изменений, метрики качества.
- Полная модель — [06-data-model.md](06-data-model.md).
- Все времена — `timestamptz` (UTC), плюс часовой пояс участника для построения «дня» (день участника — с 04:00 до 04:00 по местному времени, чтобы поздний ужин не попадал в следующий день; граница настраивается).

### 9.2. Объектное хранилище
Структура ключей: `family/{family_id}/photos/{yyyy}/{mm}/{media_id}.webp`, `.../thumbs/...`, `.../audio/...`. Политика хранения: фото — бессрочно (нужны для обучения), с возможностью удаления пользователем; аудио — 90 дней (после распознавания текст сохраняется в БД).

### 9.3. Справочники нутриентов
Загружаются в отдельную схему `ref` при установке: USDA FoodData Central, таблицы российских продуктов, CIQUAL; Open Food Facts — по запросу штрихкода с локальным кэшированием. Подробно — [03-nutrition.md](03-nutrition.md).

## 10. Безопасность

| Угроза | Мера |
|---|---|
| Перехват трафика | Только HTTPS (TLS 1.3), HSTS; WebSocket через TLS |
| Кража токена с устройства | Refresh в защищённом хранилище ОС, ротация, обнаружение повторного использования, отзыв устройства администратором |
| Перебор приглашений | Код 128 бит, одноразовый, TTL 24 ч, ограничение частоты запросов |
| Доступ к чужим данным внутри семьи | Проверка прав на каждом запросе; тесты матрицы прав |
| Утечка БД / бэкапов | Шифрование бэкапов (restic), диск VPS с шифрованием; секреты только в `.env` с правами 600 |
| Утечка в AI-провайдера | Передаётся минимум; выбор провайдера без обучения на данных клиента; возможность полностью локального режима |
| Уязвимости зависимостей | Автоматическая проверка образов (Trivy) и зависимостей при сборке |
| Злоупотребление API (утёкший токен) | Ограничение частоты по устройству, лимит стоимости AI |

Журнал аудита: вход устройств, отзыв, изменение прав, экспорт данных, удаление участника.

Права на данные: администратор может выгрузить все данные семьи (JSON + медиа в архиве) и полностью удалить участника со всеми его данными.

## 11. Надёжность, резервное копирование, мониторинг

- **Бэкапы:** ежедневно `pg_dump` + инкрементальная копия медиа через restic во внешнее хранилище (другой провайдер/облако); хранение: 7 ежедневных, 4 еженедельных, 12 ежемесячных. Ежемесячная **автоматическая проверка восстановления** во временный контейнер с отчётом в админке.
- **Целевые показатели:** потеря данных при аварии сервера ≤ 24 ч (на клиентах при этом остаются несинхронизированные записи, которые догрузятся); восстановление ≤ 2 ч по инструкции.
- **Мониторинг:** `/admin/health` (БД, Redis, MinIO, embedder, AI-провайдер, свободное место, очередь задач); метрики Prometheus: задержки API, длина очередей, задержка распознавания по этапам, доля ошибок AI, расходы. Оповещение администратору (push/e-mail/Telegram) при: недоступности компонента > 5 мин, очереди распознавания > 20 задач, диске > 80 %, неудачном бэкапе, превышении бюджета.
- **Логи:** структурированные JSON, хранение 30 дней, без содержимого фото и без персональных данных о здоровье.

## 12. Нефункциональные требования к серверу

| Параметр | Значение |
|---|---|
| Задержка API (кроме распознавания) | p95 ≤ 300 мс |
| Распознавание фото (от загрузки до результата) | p50 ≤ 3 с, p90 ≤ 5 с |
| Распознавание голоса | p50 ≤ 2 с после окончания загрузки аудио |
| Одновременные пользователи | ≥ 10 устройств без деградации |
| Доступность | ≥ 99 % в месяц (допустимы плановые обновления ночью) |
| Покрытие тестами серверной логики | ≥ 80 % для модулей распознавания (без внешних вызовов), нутриентов, синхронизации, прав |
| Документация | OpenAPI, инструкция установки, обновления, восстановления |
